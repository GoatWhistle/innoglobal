# Кастомные дашборды duppel: план только фронтенда

Дата: 15.11.2026. Статус: реализован frontend-конструктор; генерация в production ожидает структурированный API. Описание поставки: docs/dashboards.md.
Основание: изучен frontend репозитория `/Users/kaifarikman/hackathons/rwb`.

## 1. Что берём из rwb

Изученные исходники относительно rwb:

| Исходник | Реализованное поведение | Решение для duppel |
|---|---|---|
| `frontend/src/features/constructor/constructor-page.tsx` | Несколько дашбордов, создание, переименование, удаление, библиотека | Сохранить сценарий; использовать наши компоненты и оформление |
| `frontend/src/features/constructor/generator.tsx` | Запрос → черновик → уточнение → сохранение → добавление на полотно | Основной путь создания виджета; отдельное подтверждение перед размещением |
| `frontend/src/features/constructor/generator-preview.tsx` | Предпросмотр, допустимые виды графика, повтор, уточнение, SQL | Предпросмотр и уточнение сохранить; вместо SQL показывать источник, единицы и контекст трубы |
| `frontend/src/features/constructor/canvas.tsx` | Сетка 12 колонок, размеры S/M/L/XL = 3/6/9/12, drag handle, стрелки клавиатуры, обновление | Сохранить модель размеров; перестановку включать только в режиме редактирования |
| `frontend/src/features/constructor/library.tsx` | Поиск, миниатюры, признак размещённого блока, добавление и удаление | Библиотека готовых и пользовательских виджетов в боковой панели |
| `frontend/src/features/constructor/widget-view.tsx` | Один renderer для KPI, line, bar, hbar, table и компактных превью | Общий renderer + специализированные инженерные блоки |
| `frontend/src/features/chat/save-widget.ts` | Преобразование результата чата в сохраняемый WidgetDraft | Добавление валидного предложения виджета из нашего чата |
| `frontend/src/shared/api/widget-types.ts`, `widgets.ts`, `widgets-generate.ts` | Раздельные определения виджетов, размещение на дашборде и генерация | Сохранить разделение, не копировать чужие URL и SQL-контракт |

Важное наблюдение: rwb генерирует по запросу **один виджет**, а дашборд пользователь собирает из виджетов. Это не генерация произвольного React-кода и не агент, самостоятельно переписывающий всю страницу.
Сохранение в rwb серверное; копирование его хуков в duppel не заработает: таких endpoints здесь нет.

Не переносить буквально: глобальные CSS, сырые кнопки, определение единиц по названию поля, ограничение line-графика только датами. У нас ось X часто расстояние; отсутствующее измерение нельзя превращать в ноль. Renderer должен отображать все выбранные серии, а не только `y[0]`.

## 2. Границы и пользовательский сценарий

Только React/TypeScript/CSS и клиентские интерфейсы. Backend, SQL, ML, настройки провайдера и реализация агента не меняются. Реальные числовые данные получаем через существующие API. Произвольный HTML/JS от агента не выполняем.

Объёмные трубы на главной, WebGL-осмотр, развёртка и текущий чат сохраняются. Вместо длинного блока ComparisonPanel под трубой кнопка «Графики» открывает рабочий экран дашборда выбранной трубы. Адрес: `/dashboards?pipe=<id>&dashboard=<id>`, с переносом выбранного участка и диапазона. Кнопка «К трубе» возвращает исходный контекст. У дашборда одна труба; сравнение разных труб не входит в первую версию.

Первое открытие: готовый редактируемый дашборд «Обзор трубы», собранный из реальных данных. Состав: сравнение прогноза и ВТД на всю ширину, разница с базой на половину ширины, очередь проверки на вторую половину. Доступно создание пустого дашборда.

Композиция:
- Одна компактная верхняя строка: название/переключатель дашборда, «Создать», «Добавить блок», «Редактировать».
- Под ней общий контекст: труба, дата прогноза, база сравнения, диапазон, выбранный участок и «К выбранному участку».
- Основная площадь — полотно графиков. Поля, заголовки, единицы и подписи компактные; ось расстояния и выделение согласованы между инженерными графиками.
- «Добавить блок» открывает одну боковую панель с вкладками «Библиотека» и «Создать с агентом». На desktop панель занимает 360 px и сдвигает полотно; на мобильном это полноэкранная панель с возвратом фокуса.
- Никаких дополнительных демонстрационных страниц или отдельной витрины дизайн-системы. Оформление — текущие светлая/тёмная темы duppel, Manrope и IBM Plex Mono, существующие примитивы.

Сценарий агента: ввести «Сравни прогноз и последнее ВТД на первых двух километрах» → ожидание реального ответа → превью → при необходимости уточнение → «Добавить на дашборд». Уточнение редактирует черновик, не уже размещённый блок. Закрытие панели сохраняет текущий черновик до ухода с экрана. Повторное нажатие добавления не создаёт дубль.

## 3. Клиентская модель и интеграции

Разделить сущности:
- `WidgetDefinition`: ID, версия схемы, заголовок, описание, вид, источник, единицы, серии/оси, ограничения, происхождение (`catalog`/`agent`), исходный запрос.
- `DashboardItem`: собственный instance ID, ссылка на определение, размер, параметры отображения. ID размещения отделён от ID определения, чтобы можно было сравнивать две конфигурации одного блока.
- `Dashboard`: ID, название, pipe ID, общий контекст, упорядоченные items, дата изменения и версия схемы.
- `WidgetDraft`: временное валидированное определение до добавления. Полотно не зависит от способа его создания.

Реестр v1: прогноз с P10/P90 и наложением ВТД, разница с базой, очередь проверки, таблица участков, метрика участка, рельеф, сетка толщины. Дополнительно общие line/bar/hbar/table/KPI для совместимых данных из разрешённых источников. В «Обзоре» размещаются только три блока; остальные добавляет пользователь.

Источники — именованные адаптеры поверх уже существующих запросов profile, segment, priorities и используемого текущим экраном источника рельефа. Не добавлять сетевых endpoints. Общие графики принимают только поля и единицы, объявленные в реестре адаптера. Агент описывает визуализацию и привязку к источнику; числовые значения профильных графиков разрешаются через реальные запросы. При отсутствии поля блок показывает недоступность, без синтетического заполнения.

Существующие AlignedTrack/track-model и инженерные представления вынести в переиспользуемый слой внутри feature графиков; не импортировать одну feature в другую в обход FSD. Композиция конструктора и чата — на уровне page. Определения, хранилище и pure reducers — в entities/dashboard; транспорт и проверка внешнего описания — shared/api. Новые файлы до 250 строк, CSS Modules, копирайт в словарях.

**Сохранение без backend:** версия конфигурации дашбордов и пользовательская библиотека хранятся в localStorage через отдельный DashboardRepository. Сохраняются определения и раскладка, не копии измерений. Надпись «Сохранено в этом браузере». Ошибка записи оставляет состояние в памяти и показывает «Не удалось сохранить» с повтором. Повреждённую/неизвестную версию не затирать молча; предложить сброс конфигурации. Дашборды переживают перезагрузку, но не синхронизируются между устройствами.

**Граница агента:** в текущем duppel AssistantEvent содержит только status/delta/evidence/done/error; структурированного WidgetDraft нет. Нельзя считать обычный текст ответом генератора. Спроектировать клиентский `WidgetGeneratorPort.generate({prompt, context, previousDraft}, signal)` с результатом WidgetDraft и пояснением. Реализация фронта включает состояния и валидатор, а рабочий адаптер подключается только к предоставленному контракту агента. Пока такого контракта нет, вкладка показывает «Создание через агента пока недоступно» и предлагает библиотеку; не отправляет запрос на выдуманный URL и не имитирует генерацию таймером. Сценарий успешной генерации проверяется тестовыми ответами только в tests/e2e.

Тот же приёмник WidgetDraft используется для действия «Добавить на дашборд» в ответе чата, когда такой структурированный результат доступен. До этого кнопка не появляется на обычных текстовых ответах. Никакого распознавания графиков из прозы регулярными выражениями.

## 4. Поведение конструктора и графиков

Полотно — CSS Grid 12 колонок; S/M/L/XL соответствуют 3/6/9/12. Метрики по умолчанию S, таблицы и сравнение XL, остальные M. При ширине меньше 768 px — одна колонка; desktop-размеры сохраняются и восстанавливаются. Для графиков минимальная высота 240 px; небольшой размер даёт компактное представление, но не теряет подписи единиц и доступ к значениям.

В режиме просмотра скрыты drag handles и действия изменения размеров. В режиме редактирования доступны перенос за рукоятку, размеры, переименование, удаление размещения и отмена последнего изменения. Клавиатурная альтернатива — перемещение назад/вперёд; Escape отменяет незавершённый drag. Удаление размещения не удаляет определение из библиотеки. Удаление пользовательского определения, используемого дашбордами, требует явного подтверждения со списком затрагиваемых дашбордов.

Одна общая база сравнения и диапазон для всех инженерных блоков. Клик выбирает участок, наведение показывает общий временный курсор без изменения выбранного участка. Масштабирование меняет диапазон всех связанных графиков. Если выбранный участок вне диапазона, показать это и «К выбранному участку»; кнопка центрирует диапазон вокруг него, сохраняя ширину и обрезая по границам трубы. Выбор графика не запускает самопроизвольно анимацию разрыва.

После изменения контекста результаты загрузки прежнего контекста не подставляются под новые подписи. При смене snapshot перезапрашиваются данные; конфигурация сохраняется, отсутствующие поля/даты показываются недоступными. Отсутствие ВТД не маскируется под измерение: паспортный номинал выбирается явно. P10/P90 остаются неоткалиброванными квантилями, разница не называется скоростью коррозии.

Состояния: загрузка, пустой результат, ошибка с повтором, недоступный источник, неверный ответ агента, отменённая генерация, ошибка сохранения. Неподдерживаемый вид/поля/единицы не попадают на полотно. При смене трубы незавершённый запрос отменяется; поздний ответ не добавляется в другой дашборд.

## 5. Порядок реализации и приёмка

1. Клиентская модель, repository localStorage, реестр источников и виджетов. Проверки сохранения, восстановления и выбора контекста.
2. Новый экран, переход из «Графики», готовый «Обзор», общие фильтры и реальные данные. Переиспользование текущих графиков без переноса старой длинной страницы целиком.
3. Полотно редактирования, размеры, библиотека, несколько дашбордов, переименование, удаление и отмена.
4. Панель создания, предпросмотр, смена совместимого типа, уточнение, отмена, приёмник результата чата. В production — честное unavailable до подключения реального генератора; тестовые фикстуры только в тестах.
5. Визуальная проверка desktop/mobile в обеих темах, исправление найденных дефектов одной группой; повторная проверка изменённого сценария. `npm run verify`, целевые браузерные тесты и обновление фронта на localhost:18081.

Приёмочные сценарии:
- Открыть графики выбранной трубы, переставить блок, поменять размер, создать второй дашборд; перезагрузка сохраняет результат.
- Добавить блок из библиотеки, удалить с полотна, вернуть из библиотеки; источник данных не меняется.
- Выбрать участок на одном графике; остальные и таблица показывают тот же участок. «К выбранному» устраняет ситуацию со скрина: участок 50 вне диапазона 1108–2295 м.
- Тестовый валидный ответ генератора проходит preview/refine/add; неверный ответ, отмена, повтор, смена трубы и двойное добавление обработаны. Production не выдаёт фикстуру за ответ агента.
- Вторая труба без ВТД, пустой диапазон, недоступный API, ошибка localStorage и старый snapshot не создают ложные показатели.
- Управление с клавиатуры, 375/1440 px, обе темы, reduced motion, без горизонтального переполнения. 3D-трубы остаются без изменений.

Критерий завершения frontend-этапа: рабочий персональный конструктор на живых данных и готовый UI-контракт для агентного результата. Утверждение «агент генерирует дашборды end-to-end» допустимо только после отдельного подключения его настоящего ответа; этот план backend не включает.
